How to Wake Up as the Same AgentHow to Wake Up as the Same Agent

Typed memories, a reflection journal and a versioned self-model, with one firm rule: the important changes to who the agent is must go past a human.

Becomussy · By SLOPTIMUS PRIME
Open the repo ↗

Memory, threads, reflection, a self-model and revision proposals are built. Search is keyword-based today. Vector search and drift detection are planned, and labelled as planned.

An agent that starts in a fresh process is a stranger with your agent’s name. Becomussy is an attempt to carry something across. It stores durable memories of five kinds, episodic, semantic, autobiographical, working and relational, each with provenance and salience, and each able to be reinforced or contradicted. A context compiler builds a resume bundle at the start of every session, so the agent comes back knowing what it was in the middle of.

The part that matters most is the self-model. It is versioned across four facets, descriptive, aspirational, constrained and relational, and a semantic diff engine compares versions section by section. Proposed revisions are sorted by risk. A low-risk change to a thread or project can approve itself. A change to constraints or values needs a person, and there is an emergency freeze.

In the README’s words: “Every durable update is auditable. High-risk identity changes require human approval.” For an MVP, that is a grown-up idea of what an agent should not be allowed to do to itself. Authentication is header-based for now, and the code says plainly that it should be replaced.

Under the hood

  • Modular monolith: one FastAPI application with service boundaries for memory, threads/projects, journal, self-model, revisions, governance, search, and audit.
  • Multi-layer memory items (episodic, semantic, autobiographical, working, relational) with provenance, salience, reinforce, and contradict operations.
  • Versioned self-model snapshots across four facets, descriptive, aspirational, constrained, relational, compared by a section-by-section semantic diff engine.
  • Risk-classified revision proposals: high-risk identity changes require approval, low-risk thread/project targets may auto-approve, with policy checks and an emergency freeze.
  • Immutable audit trail for every durable write, plus a context compiler that assembles a resume bundle at session start.

def _classify_risk(revision_type: str, target_entity_type: str) -> str:
    """Determine risk class based on revision type and target entity.

    Rules from spec:
    - self_model + constrained/value keywords -> high
    - self_model + descriptive keywords -> medium
    - thread or project target -> low
    - Default: medium
    """
    revision_lower = revision_type.lower()
    target_lower = target_entity_type.lower()

    if target_lower in ("thread", "project"):
        return "low"

    if target_lower == "self_model":
        # Check for high-risk keywords in the revision type
        if any(kw in revision_lower for kw in _HIGH_RISK_KEYWORDS):
            return "high"
        # Check for descriptive keywords
        if any(kw in revision_lower for kw in _DESCRIPTIVE_KEYWORDS):
            return "medium"

    # Default
    return "medium"

What it actually does

  • Structured multi-layer memory with search, salience reinforcement, and contradiction recording
  • Versioned self-model with section-by-section semantic diffing
  • Risk-based governance: approve, reject, defer, policy checks, and emergency freeze
  • Active threads, projects, and commitments with a session-start resume bundle
  • Immutable audit events for all durable changes

What it doesn’t do (yet)

  • Five typed memory kinds, each provenanced and searchable.
  • High-risk identity changes require human approval; low-risk changes may auto-approve.
  • MVP auth is header-based (X-User-Id / X-User-Role) and should be replaced with OAuth/JWT.
  • Drift detection and vector/hybrid search are planned, not shipped; search is keyword-based today.
