Somewhere in every game repository there is a texture nobody can explain. It was generated once, by a tool nobody remembers, with settings nobody wrote down. MothBake is built so that file never exists again.

A recipe names the engine, the inputs and the parameters. MothBake archives the raw result, decodes it with its own in-repo decoders for PNG, GIF, ZIP, Radiance HDR, WAV and MIDI, and writes what your project actually consumes: plain files, sprite atlases, a JSON bundle, an ES module or a Godot export.

Identity is layered rather than overloaded. The recipe, the generation instance, the raw artifact, the local bake and the export each carry their own SHA-256, so a signed URL is never mistaken for a fingerprint. Determinism is tested where it can be: the ES module output is compared byte for byte with a golden file, and the ZIP writer pins every timestamp to 1 January 1980 so archives come out identical. Lose the network and mothbake repair rebuilds the built-in bakers from what was archived.

“Somewhere in every game repository there is a texture nobody can explain.”

Under the hood

  • Manifest-driven recipe → dependency plan → run journal → raw archive → local bake → candidate pipeline, with separate identities at every stage.
  • In-repo decoders and emitters: PNG (filters 0–4; colour types 0/2/3/4/6), GIF87a/89a, ZIP (stored/deflate read and write), Radiance RGBE, WAV (8/16/24/32-bit PCM and 32-bit float) and Standard MIDI, plus files/atlas/JSON/ESM/Godot emitters.
  • Layered SHA-256 content identities (recipe, generation instance, raw artifact, local bake, export) so a signed URL is never mistaken for an identity.
  • Approval-gated live execution: exact spending-plan fingerprints, a durable single-host run journal, and offline repair of built-in bakers from archived raw outputs.

/** SHA-256 hex digest of bytes; path names do not contribute to the hash. */
export function hashBytes(bytes) {
  if (!(bytes instanceof Uint8Array)) throw new TypeError('hashBytes requires bytes');
  return createHash('sha256').update(bytes).digest('hex');
}

What it actually does

  • Offline fixture runs on Node.js 20+, without runtime dependencies
  • In-repo PNG, GIF, ZIP, HDR, WAV and MIDI decoders
  • SHA-256 identities, pinned approvals and versioned export packs
  • Verified rebuilds from raw results; legacy archives marked unverified

What it doesn’t do (yet)

  • Zero runtime dependencies: every decoder (PNG, GIF, ZIP, HDR, WAV, MIDI) lives in-repo and installs air-gapped.
  • Determinism is tested per emitter/decoder (byte-for-byte ESM golden; fixed-epoch ZIP), not asserted as a global bit-exact guarantee.
  • Offline rebuild: `mothbake repair` rebuilds built-in bakers from archived raw results; billable live calls are approval-gated and off by default.

If you open the repo, start here

  • `mothbake plan` shows submissions, archive rebuilds, estimates, unknown costs and local budget violations before any spend.
  • The ESM emitter is compared byte-for-byte against a committed golden file (test/golden.test.mjs).
  • The ZIP writer pins a fixed MS-DOS epoch (1980-01-01) so archives are byte-deterministic (src/decoders/zip.mjs).
  • SHA-256 fingerprints are layered across recipe, instance, raw artifact, local bake and export: there is no single global artifact hash.
